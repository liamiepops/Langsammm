# Notes for AMO reviewers

Thank you for taking the time. This add-on contains one compiled artifact, a
WebAssembly module built from the Rust source included in this package. These
notes should let you rebuild it and confirm it matches.

## What the add-on does

It plays audio slowed down. Setting a media element's `playbackRate` below 1
drops the tempo and the pitch together, and it also drags the spectral envelope
down, which is what makes slowed voices sound wrong. The WebAssembly module
lifts that envelope back up by the same interval, so the pitch stays low while
voices keep their own character.

It runs on YouTube, SoundCloud and Bandcamp. It reads no page content, makes no
network requests at runtime, and stores only its own settings.

## Build environment

The toolchain is pinned in `rust-toolchain.toml`, so `rustup` will fetch the
right version automatically. Any operating system works. Nothing else is
needed, and there is no bundler, minifier or package manager anywhere in this
project.

* Rust 1.97.1
* target `wasm32-unknown-unknown`

## Rebuilding the binary

From the root of the source package:

```
rustup target add wasm32-unknown-unknown
cargo build --release --target wasm32-unknown-unknown
```

That writes `target/wasm32-unknown-unknown/release/langsammm.wasm`, which is the
file shipped as `extension/langsammm.wasm` in the add-on.

To confirm it matches, compare against `SHA256SUMS` in this package:

```
sha256sum target/wasm32-unknown-unknown/release/langsammm.wasm
```

**Please build from a clean tree.** An incremental build and a clean build of
identical source produce different bytes. Two clean builds agree exactly, which
is what the checksum was taken from. If you have already run `cargo test`, run
`cargo clean` before the build above.

`cargo test` runs the DSP test suite and needs no network access.

## What the binary does, and what it cannot do

It is pure signal processing. It takes blocks of audio samples in linear memory
and writes processed samples back. Concretely:

* It declares **no imports at all**. You can confirm this with
  `wasm-objdump -x` or by calling `WebAssembly.Module.imports()` on it, which
  returns an empty array. It therefore cannot call into JavaScript, reach the
  DOM, open a network connection or read anything outside its own memory.
* It is compiled without `wasm-bindgen`. The entire interface is nine
  `extern "C"` functions, all declared in `src/lib.rs`.
* The source is about 900 lines across three files. `src/fft.rs` is a radix-2
  FFT, `src/stft.rs` is the analysis and the envelope warp, and `src/lib.rs` is
  the C ABI wrapper.

## Where the other shipped files come from

Every JavaScript file in the add-on is the original source, unminified and
commented.

| shipped file | origin |
|---|---|
| `langsammm.wasm` | built from `src/`, as above |
| `bridge.js`, `page.js`, `worklet.js`, `popup.js`, `popup.html` | hand written, shipped as is |
| `icons/*.png` | generated by `node tools/icons.js`, which contains its own PNG encoder and has no dependencies |

`tools/` is included for provenance only. Nothing in it runs at build time for
the binary and none of it ships inside the add-on.

## Two things you may notice

**Two manifests.** `manifest.json` targets Chrome and
`manifest.firefox.json` is the one in this add-on. They differ in exactly two
places: Firefox declares `page.js` as a `world: "MAIN"` content script and
carries the add-on id. Chrome instead injects that file from `bridge.js`,
because Chrome governs such an injection by the extension's CSP while Firefox
governs it by the page's CSP and blocks it. `tools/check-manifests.js` asserts
that the two files agree on everything else.

**A script element in `bridge.js`.** That injection path is inert in this
build. `bridge.js` reads its own manifest, finds `page.js` declared as a
MAIN-world content script, and skips the injection. The code is shared with the
Chrome build rather than duplicated.

## Permissions and data

`data_collection_permissions.required` is `["none"]`, and that is accurate. The
add-on makes no network requests at runtime. The WebAssembly module is loaded
from the add-on's own package, and `storage` holds nothing beyond the user's
own slider positions.

`storage` is the only permission. There are no `host_permissions`.
The content scripts are limited to the three sites above, and
`web_accessible_resources` is limited to the same three, so no other origin can
load anything from this add-on.
